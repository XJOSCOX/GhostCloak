# Relay architecture — Phase 1D.3

Status: preparation only, 2026-09-11. The owner reports Phase 1D.1/1D.2 staging validation; this phase does not probe or change staging, Cloudflare, DNS, the VPS, certificates or firewall. No relay is implemented or enabled.

Current path: client → Cloudflare TLS edge → outbound Tunnel → private nginx Unix TLS socket → loopback backend → loopback PostgreSQL.

Future conceptual path: client → independently operated privacy relay → existing Cloudflare edge → existing origin path. Separating observers is the goal; a relay does not remove application metadata or guarantee anonymity.

## Transport contract

`HttpGhostClient` retains origin validation, route selection, CBOR encoding, application bearer authentication and response validation. `GhostCloakTransport.execute` accepts a `TransportRequest` containing the intended HTTPS endpoint, exact encoded POST body and application Authorization. It returns only status, content type and bounded response bytes. Neither boundary carries peer addresses or arbitrary identity headers. Implementations are trusted client code, not a sandbox: an injected malicious adapter could steal tokens or replace responses.

`DirectHttpsTransport` preserves platform URLConnection TLS and hostname verification, five-second connection/read timeouts, fixed-length POST, content type, user agent, disabled redirects/cache and bounded streaming reads. Loopback HTTP remains an explicit test-only option. `HttpGhostClient` repeats response type/size/version/schema/error validation for every adapter. Encryption, envelope format, routes, request bodies, routing, durable-outbox idempotency, fetch and ACK semantics are unchanged.

A future adapter must authenticate the configured relay and the intended application endpoint, preserve the inner body exactly, bound both encapsulated and decoded responses and use reviewed standard libraries. CONNECT requires inner TLS to the original hostname; OHTTP would additionally require authenticated gateway key configuration, standard encapsulation and a compatible gateway. An interface alone does not make OHTTP deployable against today's backend. Never rewrite the application origin/audience to the relay hostname, accept certificate mismatch, install a trust-all verifier, bypass CA validation or redirect bearer credentials. Platform trust remains in force; no new certificate pin set is introduced. See [TLS policy](TLS_POLICY.md).

## Independent authentication

Application credentials remain in `AccessTokenStore`/endpoint state and go only in the inner request to the application endpoint. Future relay provisioning must use a separate relay-scoped credential source, audience, storage namespace, lifetime and revocation flow. A relay adapter would receive that source at construction, independently of `HttpGhostClient`; its outer proxy authorization must never be copied into application Authorization or forwarded to the backend. Application tokens, usernames, device keys and routing IDs must never double as relay credentials. No relay credential format, anonymous credential protocol or Privacy Pass implementation is introduced here.

A CONNECT relay forwarding inner TLS cannot read the application bearer. A TLS-terminating HTTP forwarder can, and therefore fails the preferred account-separation goal. OHTTP hides inner HTTP from its relay but not its gateway. Independent authentication does not itself guarantee unlinkability: paid accounts, stable relay tokens, colluding operators, timing and traffic volume can reconnect observations. Cloudflare still reads the inner bearer when it terminates application TLS, even after a CONNECT relay replaces the source IP. Login bodies and token-grant responses let Cloudflare map sessions to account/device IDs; token rotation does not erase that link.

## Candidate comparison (design assessment, not benchmarks)

Here “HTTP forward relay” means an application-level HTTPS forwarder that terminates client TLS and creates a second HTTPS request. HTTPS proxying with an opaque CONNECT tunnel belongs in B. Double-hop and self-hosted describe deployment choices, not new encryption protocols. All options retain message E2EE if implemented correctly, but its clear routing envelope is not message plaintext.

| Option | Client IP and destination visibility | HTTP path/contents visibility | Latency and mobile suitability | Deployment, complexity, cost/dependency | Abuse implications |
|---|---|---|---|---|---|
| A: HTTPS forward relay | Relay knows client IP and API; Cloudflare sees relay egress | Relay, Cloudflare and backend see inner HTTP including bearer and envelope; E2EE payload stays encrypted | Extra hop/TLS; ordinary short requests suit mobile, with radio/latency cost | Familiar HTTP stack, moderate operations; egress/hosting expense, portable providers | Relay can enforce network limits but now holds reusable app tokens; shared egress can trip edge limits |
| B: HTTP CONNECT / MASQUE | Single relay sees client IP and destination hostname/port; Cloudflare sees relay IP | With inner TLS to API, relay cannot read HTTP; Cloudflare/backend can | Extra setup/hop; connection reuse helps, mobility/UDP blocking/reconnects need measurement; HTTP CONNECT is TCP, MASQUE CONNECT-UDP can carry QUIC | Requires compatible client/proxy support and TLS layering; higher complexity than A; managed access or self-hosted bandwidth cost | Destination/port allowlists, relay auth and quotas needed; open-proxy abuse and shared-egress blocking |
| C: OHTTP | Relay knows client IP and gateway; gateway sees relay IP; service destination may be inferable from gateway name | Relay sees outer request size/time, not encapsulated HTTP; gateway decodes HTTP, downstream backend sees it; Cloudflare sees inner data only if on decrypted leg or acting as gateway | Extra encapsulation/hop, suited to bounded request/response; polling and key refresh incur mobile cost | Standard library, authenticated key discovery and new gateway required; substantial integration; provider access/hosting costs | Gateway cannot depend on source IP; stable inner app IDs still correlate activity; relay/gateway quotas and replay policy need review |
| D: Double-hop | Noncolluding ingress knows client IP and next hop; egress knows API and ingress IP; Cloudflare sees egress | With end-to-end application TLS, neither relay reads HTTP; Cloudflare/backend do | Two hops, added handshakes, mobile loss/reconnect and battery costs | Two independent operators/jurisdictions and layered authentication; highest operational coordination and two egress bills | Split abuse handling, shared IP false positives, collusion or joint logs defeat separation |
| E: Self-hosted relay | Operator knows client IP and usually API; Cloudflare sees relay IP; same operator as backend can join both views | Depends on A/B/C chosen; TLS forwarder sees contents, CONNECT forwarder does not | Depends on geography/capacity; small anonymity set and single-region mobile latency | Full patching, capacity, uptime and abuse responsibility; no managed-product dependency, ongoing hosting/egress cost | Must restrict destinations/authenticate; small user pool easy to correlate, provider can suspend for abuse |

Protocol bases: [HTTP CONNECT, RFC 9110 §9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6), [CONNECT-UDP, RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.html), and [OHTTP, RFC 9458](https://www.rfc-editor.org/rfc/rfc9458.html). The operational tradeoffs above are Ghost Cloak design assessments, not provider guarantees or measured performance.

## Provider portability

Checked official public documentation on 2026-09-11: [Cloudflare Privacy Proxy](https://developers.cloudflare.com/privacy-proxy/) is MASQUE-based and labelled Enterprise-only. [Privacy Gateway](https://developers.cloudflare.com/privacy-gateway/) is labelled Enterprise-only and describes closed-beta availability to selected companies/partners. Its [setup documentation](https://developers.cloudflare.com/privacy-gateway/get-started/) requires client key configuration and an application gateway. Availability can change; public documentation does not establish this account's entitlement, pricing or suitability. Neither product is a dependency, selected vendor or deployment commitment. Another standards-compatible relay must remain possible. Using Cloudflare both as relay and API edge would reduce operator separation even where protocol roles differ.

## Failure, DNS and rollout

| Mode | Selection and failure policy | DNS implications |
|---|---|---|
| Standard (current) | Direct existing Cloudflare path; existing bounded outbox retries/TTL; no public-origin fallback | Platform resolver resolves API hostname. ISP/resolver may observe DNS; no new encrypted DNS guarantee |
| Private relay (future) | `TransportPolicy` requires both explicit feature enablement and a supplied adapter; missing/disabled relay yields `relay_unavailable`. Adapter outage propagates; no direct retry branch | Resolve relay bootstrap locally as needed. Prefer relay-side destination resolution (CONNECT hostname or gateway), avoid pre-resolving API locally. DNS, SNI, resolver choice and fallback must be tested |
| Ghost Mode | Separate future feature; no implementation, selector or promise in this phase | Undecided, requires separate threat review |

There is no privacy-mode UI or fallback preference yet. Future user-facing controls must explain visibility before selection; private relay fails closed by default. Any eventual direct fallback must be a separate explicit user choice with visible privacy consequences, never inferred from connectivity failure. Relaunch, retry, network switch and key-refresh failures must preserve mode. Existing deduplication and TTL still bound retries; outages can lose availability and expire queued messages. Relay DNS beyond the ISP does not hide the relay connection itself or prevent destination inference and global timing correlation.

## Abuse and traffic analysis

Keep edge/relay network reputation separate from application policy. Current application controls use device-derived or shared anonymous rate buckets, session authentication, bounded challenge/prekey issuance, per-sender submissions, destination binding, mailbox capacity and recipient-only fetch/ACK. There is no client-IP principal and no claim of a new contact-consent delivery capability. Registration farming/distributed abuse and contention in the shared anonymous budget remain risks. Future delivery capabilities need independent design. NAT, VPNs and shared relay egress can cause edge false positives; do not “fix” this by forwarding trusted client-IP headers into application quotas.

Padding request/response size buckets could reduce length precision but leaves bucket, frequency and flow linkage. Timing normalization, batching and cover traffic could reduce some correlations while adding delay, radio wakeups, battery drain, bandwidth and mobile-data charges. Existing ciphertext/body-size limits and offline/outbox semantics would need explicit versioned review before padding. No padding, cover traffic, encrypted DNS or always-on connections are added. Low-latency interactive messaging remains vulnerable to a global observer correlating both ends.

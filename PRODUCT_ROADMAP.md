## SECURITY/PRIVACY CONSIDERATIONS

**Presence, typing and read receipts:** Defer all three. Typing/presence disclose activity windows and relationship timing; read receipts disclose when a person opened content and can create social pressure. They require deliberate defaults, per-contact consent/controls, abuse review and metadata measurements, not merely a UI switch. Current `Delivered` remains transport acknowledgment and must never be relabeled “Read.” If ever built, an E2EE control still leaves traffic timing/recipient correlation visible to the service; lack of a plaintext server column does not eliminate metadata.

**Message control:** “Delete for me” already exists locally. “Delete for everyone,” remote edit and undo-send should not be promised as erasure or recall: a recipient may have received plaintext, saved a copy, used another client or photographed it. A future remote delete/edit can only be an authenticated **request to cooperating clients**, with explicit timestamps, version/conflict handling, expiry and an honest UI label. A short local undo can delay submission, but adds a queue/cancellation race and does not undo after server acceptance. Forwarding/copy/share exports plaintext beyond Ghost Cloak controls; keep View Once and hidden requests excluded and require an explicit user action. Screenshot blocking/warnings are best-effort UI signals, not proof a recipient cannot capture content. No remote mutation is recommended for P2.

**Rich media:** Reply references must be authenticated and bounded. Reactions reference stable message IDs and need replay, deletion and expiry rules. Voice should use the existing encrypted attachment pipeline only after defining a new capability, duration exposure, recording permissions, bounded waveform generation/storage, playback lifecycle and safe cancellation. Waveforms/duration are message metadata if placed in plaintext descriptors; prefer encrypted payloads and coarse/minimal duration. View Once voice may be useful later but must inherit the destructive reveal boundary, not the ordinary cache. Compression and thumbnail generation need file-format/parser limits and EXIF removal. Multiple attachments require atomic or clearly partial UI semantics. Video, GIF/sticker, location and contact cards each expand parser/disclosure surface; location/contact sharing must be explicit and precise about what is sent.

**Profiles:** Keep the public Ghost Cloak ID distinct from non-unique display names and local aliases. A local alias should never sync or appear in server requests. Optional photo/About should use authenticated E2EE profile updates to accepted contacts, with a user-visible audience and revocation limits: recipients can retain a previously received profile. Do not introduce searchable usernames or a plaintext server name to implement profile discovery.

**Battery and network:** Current 2–5-second foreground polling trades immediacy for repeated requests; 30-minute periodic WorkManager cannot guarantee prompt background delivery because Android can delay periodic work ([Android WorkManager reference](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest)). First measure fetch frequency, bytes, wakeups and battery on representative devices, then consider bounded backoff/long polling or a content-free push wake-up. Push can improve latency but registers a device token with a provider and reveals wake-up timing; it needs opt-in/privacy design and a fallback path. No sync architecture changes belong in P1.

## BACKEND/PROTOCOL DEPENDENCIES — preliminary architecture only

**Groups after one-to-one polish:** Begin only after P2 and the short-term organization/voice priorities are evaluated and a dedicated group threat model is approved. A group needs an unguessable group ID, authenticated membership epochs, admin/invite authority, explicit membership-change and removal/rekey rules, replay/idempotency handling, and E2EE group name/photo. Pairwise fan-out is simpler to reason about for small groups but increases ciphertext sends and exposes sender-to-recipient edges; sender keys improve efficiency but add key-distribution, rotation and removed-member exclusion complexity. Invite links can leak membership intent and enable abuse, so should be revocable/bounded. A server-managed roster leaks the social graph; client-managed state has consistency and recovery costs. Signal's published designs illustrate both pairwise fan-out and more complex private-group administration, but Ghost Cloak needs its own reviewed contract rather than assuming their guarantees ([Signal group design](https://signal.org/blog/private-groups/), [Signal private-group system](https://signal.org/blog/signal-private-group-system/)). No group implementation is authorized by this roadmap.

**Calling after reliable asynchronous voice:** WebRTC needs authenticated signaling, ICE/STUN/TURN, call setup/cancel and missed-call policy, network-change handling, foreground/background permissions, and an explicit media E2EE identity binding. Direct ICE candidates can reveal peer IP addresses; a relay-only TURN policy reduces that exposure at latency, cost and availability tradeoffs. TURN still observes endpoints/timing/volume, and signaling can expose caller/callee/call times. Call notifications must be generic under App Lock; media keys and safety-number behavior need separate review. See the [WebRTC TURN guide](https://webrtc.org/getting-started/turn-server) and [ICE candidate privacy guidance](https://developer.mozilla.org/en-US/docs/Web/API/RTCIceCandidate/address). No call implementation is authorized by this roadmap.

**Multi-device after a device/account model redesign:** Current product behavior is one local identity/device per account. Linking would need an authenticated QR pairing ceremony that cannot be replaced by an ID scan, distinct device credentials/prekeys and device IDs under one account, per-device ciphertext fan-out, E2EE key/history transfer with explicit scope, device listing/revocation, offline/replay handling and a safety-number policy when the device set changes. A compromised or revoked device may retain previously decrypted history. The current V007/V008 schema, registration and mailbox assumptions must be reviewed before promising linked-device continuity. This should follow one-to-one UX polish and group/calling priority decisions, not be smuggled into account recovery.

The practical order is **P2 find/respond → P3 organization and local controls → P4 voice/media → group/multi-device/calling design only when the corresponding privacy and operational budgets are accepted**. An optional clean reviewed-build replay and the remaining A2+ assurance work remain separate from this product roadmap; P1 does not start them.

## P2 — FIND AND RESPOND (IMPLEMENTED FOR UPDATED ANDROID CLIENTS)

One-to-one text replies now carry a bounded envelope reference and source kind inside the authenticated Signal payload. Local message and outbox records have optional fields with defaults, so existing stored conversations decode without a database migration. The new decoder still accepts ordinary legacy payloads. Reply-capable clients must be updated together: the new reply payload type is intentionally rejected by older clients that do not recognize it. A later capability/compatibility design should decide whether to offer a plain-text fallback for mixed client versions.

The composer shows the target and can cancel. Replies to text, attachments, disappearing messages and View Once items resolve the reference only within the current visible conversation. If the original is gone, the quote becomes a generic unavailable/expired label. View Once content is always represented by a generic label, including after reveal. Pending/failed outgoing messages without a durable envelope ID cannot be selected as reply targets.

Conversation search filters the already-authorized in-memory UI snapshot; it has no server request, persistent index or analytics. Hidden requests, blocked contacts, View Once and expired/deleted items are excluded. Search is cleared when leaving the conversation. Long-press now offers state-aware Reply, sensitive Copy for normal text, and Delete for me. Existing attachment open/download controls remain on the attachment bubble.

P3 should start with per-chat mute/archive/pin and an explicit local alias editor, then assess captions and attachment composition. Mixed-version reply capability negotiation, reply-target accessibility polish and a larger-scale search performance replay are follow-ups before final release assurance. No read receipts, presence, typing, groups, calls or multi-device features were added in P2.

## P3 — LOCAL ALIASES AND CHAT ORGANIZATION (IMPLEMENTED FOR UPDATED ANDROID CLIENTS)

Accepted contacts now have an editable, removable local alias. The display order is local alias, authenticated remote name, then Ghost Cloak ID. The alias is stored only in the encrypted local contact record; it does not alter identity trust, safety numbers, addressing or peer-visible profile data. Message requests cannot be aliased before acceptance.

Accepted chats can be pinned, archived and muted locally. The main list shows pinned chats first, then unpinned chats; each group is ordered by the latest visible conversation activity with stable name/ID ties. Requests are never pinned and their message content does not affect ordering. Archived chats have their own screen, retain unread indicators and remain active. A new authenticated incoming message automatically unarchives its chat. Muting suppresses generic local notifications while delivery, ACKs and unread counts continue normally. Requests and blocked contacts cannot use these organization controls. All three flags have backward-compatible defaults in the encrypted local contact record. There is no backend, protocol or server database change.

**Recommended P4 scope:** voice notes, attachment captions and a modest media-composition improvement, beginning with a capability and privacy review. Voice needs bounded recording/playback and cancellation, while captions need authenticated payload compatibility and clear View Once/disappearing behavior. Do not add groups, calling, presence, typing or read receipts as part of that work.

## P4 — VOICE NOTES AND ATTACHMENT CAPTIONS (IMPLEMENTED FOR UPDATED ANDROID CLIENTS)

Voice notes reuse the existing locally encrypted attachment upload and authenticated message envelope. Recording uses Android MediaRecorder with AAC audio in an MPEG-4/M4A container, mono 16 kHz at 32 kbps, capped at five minutes and 4 MiB. The app requests microphone permission only when recording is invoked. App-private plaintext scratch is deleted after encryption, on cancel/error, and during orphan cleanup on startup; as with other attachments, Android's managed memory and filesystem cannot provide a physical erasure guarantee. Playback is local, one note at a time, with pause and seek; it stops when app content is hidden or locked. Duration and optional caption are inside the encrypted message payload. View Once voice is deferred because ordinary playback/cache behavior cannot safely implement its reveal boundary.

Photo, document and voice captions are bounded to 512 UTF-8 bytes in the authenticated payload. The composer previews one attachment at a time and allows caption editing or cancellation before send. Captions are available to local search and reply previews only while the message is visible. View Once photo captions are disallowed; disappearing messages remove their caption and attachment access on expiry. A peer must advertise the media capability in an authenticated message before voice or captioned attachments are sent; existing uncaptioned photo/document messages retain the legacy format. Both clients should update before using P4 media.

Photos continue through the existing decode-and-re-encode JPEG preparation path, which removes source EXIF/location metadata. Document names remain inside the encrypted descriptor, with path-safe display/open handling; documents themselves can retain embedded metadata. No backend deployment or database migration is required. Albums, transcoding, transcription and View Once voice remain out of scope.

**Recommended P5 scope:** reactions and focused message controls, with authenticated references, replay/expiry rules, and honest removal semantics. Defer groups and calling until their separate privacy and operational designs are reviewed.

## P5 — REACTIONS AND FOCUSED MESSAGE CONTROLS (IMPLEMENTED FOR UPDATED ANDROID CLIENTS)

Six fixed emoji reactions use a dedicated authenticated Signal control. The target is an envelope message ID scoped to the accepted conversation; the sender is implied by the authenticated peer. A per-target, per-sender increasing sequence makes duplicate and delayed older controls idempotent even when mailbox deliveries are reordered. An encrypted local reaction record retains the latest sequence, including a remove tombstone. Reactions are removed with the target message, including on disappearing-message expiry or local deletion. Missing, cross-conversation, blocked, hidden-request and View Once targets are ignored. Reactions do not enter search or create a separate notification. The conversation snapshot reads reaction records once, then attaches compact badges to visible messages.

Text messages advertise reaction support inside authenticated padding. A sender offers reactions only after the peer advertises support; both clients must update before reacting. Older stored messages and uncaptioned media retain their existing formats. There is no backend reaction state or database migration.

The action sheet adds React and a local Details view without internal routing, account, device, submission or envelope IDs. A pending outgoing message can be retried only through its existing durable outbox entry, retaining the submission ID and ciphertext. An ambiguous or terminal failed attempt is not resent because a second encryption/submission could duplicate delivery; the UI explains that retry is unavailable. Delete for me remains local. Delete for everyone is **deferred**: a future control could only request deletion from participating updated clients. It could never guarantee erasure after a recipient has viewed or copied plaintext. Any future design must define sender-only authority, compatibility, attachment-cache cleanup, reply fallback, reaction cleanup and expiry ordering before implementation. Editing and forwarding remain deferred.

**Recommended P6 scope:** optional encrypted profile photo/About shared to accepted contacts, with explicit audience and recipient-retention limits. Keep groups and calling as separate architecture work.

## P6 — ENCRYPTED PROFILE PHOTO AND ABOUT (IMPLEMENTED FOR UPDATED ANDROID CLIENTS)

The local profile has a display name, optional About text, optional photo and a monotonic revision. Sharing is explicit and applies only to accepted, unblocked contacts. A contact request, directory result or unknown sender never carries or displays About/photo. A local alias remains the highest-priority label and does not alter verification or the authenticated identity. Recipients accept only a newer revision, ignore duplicates and delete the previous local photo when the update removes it. Profile edits made while offline are durable; superseded pending updates are cancelled before upload so the latest revision is sent. Blocking or removing a contact clears its locally cached profile and pending share intent. Safe Exit and inactivity destruction remove the encrypted local profile records with the rest of app-owned state.

The photo is center-cropped to a square no larger than 256 × 256, re-encoded as JPEG, and stripped of source EXIF/GPS and other JPEG application/comment segments. Its encoded limit is **8,192 bytes**; About is limited to 256 UTF-8 bytes. The worst padded profile control is 8,704 bytes against the 16,384-byte Signal body limit, leaving at least 7,680 bytes of headroom; the HTTP and ingress limits are larger. Recipients validate encoded length, JPEG structure, dimensions and a bounded decode before displaying a thumbnail. Profile controls, including photo bytes, remain entirely inside Signal ciphertext and encrypted app-private storage. The server stores only ordinary encrypted-message data; P6 needs no backend deployment, persistent photo blob or database migration.

Updated peers advertise support in authenticated message padding. The new control is sent only to an accepted peer that advertised support. An older peer continues to receive the legacy encrypted display-name update and can continue messaging, but does not receive About or photo. A contact's shared name, About and photo are user assertions, not identity verification; the safety-number check remains separate. Final release assurance should replay this flow on a clean reviewed Android build. Groups and calling remain separate design work.

**Recommended P7 scope:** richer local notification controls, keeping generic content and private contact metadata as the default. Treat delete-for-everyone as a separate protocol and retention design, and groups/calling as larger architecture work.

## P7 — LOCAL VOICE MASKING FOR VOICE NOTES (ANDROID IMPLEMENTATION)

The voice-note composer offers Original, Subtle, Strong and Synthetic. Masking runs on-device before the existing encrypted attachment preparation. The selected preset is local UI state; recipients get an ordinary AAC/M4A voice note and the server receives only the existing attachment ciphertext and metadata. No backend deployment, migration or new dependency is required. The default is Original. A global default setting is deferred.

The transformer decodes bounded mono 16 kHz AAC into PCM, applies pitch-changing resampling and overlap-add timing correction, then applies preset-specific spectral shaping before encoding AAC/M4A. Strong changes pitch and resonance; Synthetic also adds a mild fixed-carrier effect. These are perceptual transformations, not measured biometric defenses. The app verifies the result's format, size, duration and decodability before encryption. A failed transformation never falls back to the original. The original and masked files remain in private no-backup scratch, with deletion on send, cancel, lock and startup sweep. During an active compose session, the original remains briefly available to switch presets and preview; it is removed before masked attachment encryption. Preview is local and stops when the composer closes or app content is hidden.

Voice masking changes vocal characteristics to reduce recognizability. It does not guarantee anonymity. Accent, speech patterns, background voices, room acoustics, music and other sounds may still identify someone or their surroundings. View Once voice, transcription and noise removal are deferred.

**Recommended P8 scope:** richer privacy-preserving notification controls with generic content as the default. Delete-for-everyone needs a separate authenticated protocol and retention design; groups and live calling remain larger architecture projects.

## P8 — PRIVACY-PRESERVING NOTIFICATION CONTROLS (ANDROID IMPLEMENTATION)

The local Notifications setting offers Maximum privacy (default), Contact only and Content preview. Contact names use the local alias before the accepted display name. Content previews are bounded to 100 characters and contain no filename, profile photo, reaction or reply target. Attachments without captions use generic media labels. View Once never enters a notification body; message requests never expose an unauthenticated name or content. Disappearing messages remain generic so plaintext does not linger in Android's notification history. Muted and blocked chats do not produce normal alerts. The existing identity-change warning remains in the app's security UI and is not controlled by chat mute; P8 does not introduce an OS security-alert channel.

App Lock forces generic alerts whenever content is protected. All notification objects use `VISIBILITY_SECRET` for the device lock screen, have no Person/conversation shortcuts, and open only the root Activity through an immutable intent. No inline actions are available. Notification preferences stay in app-local storage and are cleared by Safe Exit. Android may retain notifications in system history after Ghost Cloak updates or cancels them; users should choose Maximum privacy if that retention matters. P8 needs an Android update only, with no backend deployment or database migration.

**Recommended P9 scope:** design delete-for-everyone as an authenticated protocol and retention change before implementation. Groups and calling remain separate architecture decisions.

## P9 — AUTHENTICATED DELETE FOR EVERYONE (ANDROID IMPLEMENTATION)

An updated sender can request deletion of a server-accepted message through a Signal-encrypted control containing only its envelope ID. The receiving client uses the authenticated session sender and conversation-scoped ID to remove only that sender's earlier message. There is no plaintext deletion endpoint, server-side blob deletion, recipient deletion receipt, backend deployment or database migration. The action appears only after the peer advertises support inside authenticated message padding; older clients continue messaging and may ignore the request. Pending messages that have not been server accepted offer only **Delete for me**. There is no arbitrary age window or wall-clock authority, though delivery and retention still limit what a recipient can process.

The message remains as a minimal “This message was deleted” placeholder. The client scrubs its body, attachment descriptor, reactions and notification ledger entry; releases app-private attachment references and closes in-app media access; removes it from search; and shows “Original message deleted” in replies that reference it. A conversation-scoped tombstone blocks a late original or reaction from restoring content. View Once deletion cannot reopen consumed content, and deletion does not extend a disappearing message's lifetime. The sender's local scrub and durable encrypted outbox enqueue commit together. Offline UI says the delete request is pending; after server acceptance it says sent, never that the recipient deleted its copy.

**Blocked-sender policy:** blocked envelopes retain the existing authenticate/ratchet/ACK/discard path. Their encrypted application content is not parsed, including delete controls. A blocked recipient may keep a previously received message, and the sender gets no special response revealing block state. Hidden request content can be deleted before acceptance without exposing its plaintext. Delete for everyone is best effort: older or blocked clients, external viewer copies, screenshots, copied text, recordings and Android notification history may retain content. It does not provide forensic flash erasure.

**Recommended P10 scope:** evaluate message editing as another authenticated, terminal-control design with explicit compatibility and retention semantics. Group messaging and live calling still require separate architecture and threat-model work.

## P10 — AUTHENTICATED TEXT MESSAGE EDITING (ANDROID IMPLEMENTATION)

The sender can edit a server-accepted text message or text reply when the active, unblocked peer has advertised edit support inside authenticated message padding. An edit is a Signal-encrypted control carrying the conversation-scoped target envelope ID, a positive monotonic revision and replacement text. The original is revision 0; a higher revision replaces visible text, while equal/older revisions are ignored. A delayed original receives the latest authenticated pending edit before being stored. Older clients continue messaging; they may ignore an edit and are not promised updated text. Photos, documents, voice notes, captions, View Once and system controls are not editable.

The sender's new text and durable encrypted-outbox intent commit together. The UI shows **Edit pending** while offline and **Edited** after server acceptance; it never claims the recipient processed the edit. Only one edit per message may be pending, so an older pending plaintext revision is not retained in another outbox entry. A terminal ambiguous failure shows **Edit not sent**; the user may issue a new higher revision instead of unsafe automatic re-encryption. Search and dynamically resolved reply previews use current text. Reactions remain on the same target. Editing does not restart a disappearing deadline. Delete-for-everyone remains terminal and clears any pending recipient edit; a delayed edit cannot restore a deleted target.

Blocked envelopes keep the existing authenticate/ratchet/ACK/discard path without parsing edit content. Edits to hidden, unaccepted requests are ignored without revealing text. Ghost Cloak does not retain an edit-history UI or old plaintext in active message, search, reply-preview, notification-ledger or edit-control records. This is logical app-state replacement, not forensic flash erasure; recipients may already have seen, copied or captured earlier text. No backend deployment or server DB migration is needed.

**Recommended P11 scope:** richer local account and privacy controls, or a separate group-messaging architecture and threat-model phase. Do not fold groups or calling into text editing.

## P11 — LOCAL ACCOUNT AND PRIVACY CONTROLS (ANDROID IMPLEMENTATION)

Settings now links to one Privacy page covering messaging defaults, media, profile sharing, notification privacy, device protection and safe account information. The new defaults live in the encrypted local endpoint store and are destroyed with it by Safe Exit or Inactive Device Protection. Missing records preserve privacy-first upgrade behavior: disappearing Off, voice mask Original, and manual media downloads. Notification privacy continues to use the existing P8 preference and defaults to Maximum privacy. Global defaults never rewrite an existing chat's timer.

A new accepted conversation snapshots the current disappearing default. Its actual timer is sent through the existing encrypted per-chat control and durable outbox; acceptance leaves a durable pending marker until the control is enqueued, so offline or interrupted acceptance can resume. A new voice note preselects the local default, but the sender can change its mask for that note. Automatic photo, voice-note or document downloading is opt-in per type and uses only newly authenticated, accepted, unblocked, nonexpired, non-View Once messages while foreground access is allowed. The default is manual. No preference is sent to the backend.

Downloaded ciphertext remains linked to its message until normal expiry/deletion. An explicit, confirmed **Clear downloaded media cache** action removes downloaded ciphertext while keeping messages, descriptors, sent uploads and identity/session state. Media can be downloaded again only while the server copy remains available. Fixed 1/7/30-day automatic eviction is deferred because the server may already have expired the only remotely recoverable copy; this avoids silently making visible media unavailable. Decrypted scratch keeps its existing immediate cleanup. Cache size is computed only on request, not during Settings composition.

The existing encrypted profile-sharing switch remains global to name, About and photo; separate audience switches would add protocol and compatibility complexity. Disabling it stops future updates but cannot erase data already received by a contact. Re-enabling queues the current profile revision through the existing encrypted sync. Contact requests and blocked contacts remain excluded. The Privacy page links to existing App Lock, Safe Exit and Inactive Device Protection rather than duplicating their state. FLAG_SECURE is already applied by MainActivity; no new screenshot toggle is added. Android's sensitive-clipboard flag remains in use, while automatic clearing is deferred because it could overwrite a newer clipboard item without a reliable ownership check. There is no cloud chat backup or plaintext export.

**Future account deletion:** a public deletion API would need fresh authenticated intent, destructive removal of server account/device credentials, prekeys, sessions, mailbox and attachment ownership, plus explicit handling of local identity and recovery consequences. Safe Exit destroys local state, not the server account. P11 does not add account deletion or a server migration.

**Recommended P12 scope:** group architecture design only: group identity, membership and invitation model, admin roles, key management and membership-change rekeying, metadata/privacy boundaries, offline delivery and backward compatibility. Do not implement groups until this design is reviewed.

## P12 — PRIVATE GROUP ARCHITECTURE (DESIGN COMPLETE; NO IMPLEMENTATION)

[GROUP_ARCHITECTURE.md](GROUP_ARCHITECTURE.md) recommends pairwise Signal fan-out for a maximum of five members including the owner, with group state and profile inside E2EE envelopes and no server group roster. A single designated coordinator orders authenticated membership revisions; removal advances the epoch and excludes the removed endpoint from later-epoch fan-out. This is a design proposal with explicit offline, fork, metadata and old-history limits, not a working group feature. The currently pinned libsignal 0.102.1 does contain sender-key APIs, but using them would require a separate cryptographic design/review. Current SEND and submission quotas also block ordinary group use without a separate capacity review.

**Recommended P13.1 scope:** group identity and state foundations only. Finalize actor/coordinator signing and authorization, canonical hash-chain/fork behavior, epochs, offline resync, encoded-size and replay bounds, and state-machine tests. Keep models dormant until the security and capacity gates are resolved; do not launch group messaging in P13.1.

# Phase 1M — Inactive Device Protection

Status: implemented as an opt-in local protection with Off as the default. Settings offers 7, 14, 30, 60, and 90 days. App Lock must be enabled. This is **not** a promise to erase at an exact real-world deadline while the phone is powered off.

## Security contract and time model

Only a correct normal App Lock PIN or successful strong biometric **unlock** refreshes the timing anchor. The new anchor is durably written before UI access is granted. Wrong PIN, biometric cancellation/failure, opening the app, background sync, notifications, messages, and attachments do not refresh it. Enabling first records an anchor after fresh normal management authentication. Changing a duration preserves the prior anchor; shortening may immediately reach the deadline.

`InactivityProtection` uses injected clocks. The versioned, bounded, no-backup `inactive-protection.v1` record contains only period, boot count, authenticated `elapsedRealtime`, authenticated wall observation, and highest observed wall observation. It contains no account or contact identifier. `DurableInactivityStore` uses `AtomicFile`, explicit file and directory sync, and readback. Corrupt or unavailable records fail closed. Safe Exit cleanup removes and verifies this record with the other app-owned files. No Android database migration is involved.

Within the **same known boot**, a matching boot count and nondecreasing `elapsedRealtime()` are required. At `elapsedRealtime - authenticatedElapsed >= selected period`, the existing `LocalOperationGate` durably arms the existing Safe Exit journal before normal access. Its recovery coordinator destroys keys, cleans storage, verifies the fresh baseline and returns to onboarding; an interrupted operation remains on the fail-closed Retry screen. No new destruction engine exists. The check runs synchronously before normal owners on process startup, on Activity start, and in the existing local maintenance loop. Correctness does not depend on that loop running continuously: the next startup or resume checks again.

Every **cross-boot** case, unavailable boot count, or monotonic regression is `TIME_UNCERTAIN`. The wall clock is user adjustable and cannot independently prove powered-off duration. Therefore `PROVABLY_EXPIRED` has **no cross-boot qualifying evidence under this local-only policy**. No forward wall jump, apparent ordinary progression, or rollback can authorize destruction. Two powered-off histories with identical local observations get the same protected state. This intentionally supersedes the earlier proposed cross-boot clear-expiry test. Android documents [`elapsedRealtime()` as time since boot](https://developer.android.com/reference/android/os/SystemClock); [Keystore wall-time checks are software enforced](https://source.android.com/docs/security/features/keystore/features).

`TIME_UNCERTAIN` prevents normal runtime/network initialization, WorkManager fetch, contacts/message rendering, and media access. Only the encrypted App Lock record is opened through an isolated storage path. The user sees the normal PIN/biometric challenge; failed or cancelled attempts remain locked. A correct normal unlock durably records a new boot/monotonic anchor before access. A persistence error leaves the app fail closed; it never substitutes an OFF setting. Notification content remains generic and existing `FLAG_SECURE` remains active. A same-boot expired state cannot be reset by authentication.

## Administration

Settings → Privacy & Security → Inactive Device Protection shows the period and accurate warning: “Ghost Cloak automatically clears local data after the selected period when the device can securely determine that the inactivity limit has expired. If device time cannot be trusted after a restart, Ghost Cloak remains locked until you authenticate.” Enabling needs fresh MANAGE authentication and explicit acknowledgement. Every change needs fresh MANAGE authentication. Disabling also needs confirmation. Extending or disabling when a Safe Exit PIN exists also needs the current Safe Exit PIN through the existing throttled administration challenge. App Lock cannot be turned off while protection is enabled. A profile with App Lock OFF cannot enable it. Safe Exit PIN verification is never treated as normal activity.

## Scope and limits

This feature uses no server/API timestamp, network event, analytics, foreground service, alarm, server/database migration or backend change. Server operators never receive the setting, deadline, unlock timestamp or trigger. Android force-stop is respected: the next launch evaluates the record before private content. Background activity cannot extend the interval. If the device remains off for longer than the configured period, automatic erasure cannot be proven locally after reboot; the protection is owner authentication, not a guessed destructive action. The wall clock high-water is retained for limited local evidence but is never wipe authority.

Validation: 106 JVM tests passed, including injected-clock exact boundary, same-boot recreation, ambiguous reboot/rollback/forward-jump, failed writes, administration credentials, and preserved anchors. Strict dependency verification, debug and release builds, and release vital lint passed. On disposable `emulator-5554`, 26 App Lock/background sync/Safe Exit/inactivity tests passed. Separate AVD probes verified an actual reboot enters TIME_UNCERTAIN; an existing synthetic identity showed only the PIN screen after a process restart, remained locked on wrong PIN, and became available after correct PIN; and a proven same-boot expiry used the existing destruction coordinator and cleared the timing record. Existing AVD Safe Exit tests cover offline cleanup, interrupted recovery, retry, and fresh onboarding. No important physical phone or VPS was accessed.

# Phase 1L.1 — anonymous contact identity design and migration audit

Status: design and source audit only, 2026-10-03, current source at `1fbbefe`. No schema, protocol, app, recovery, or server behavior changes in this phase. This is a target state, not a claim about the deployed VPS. No live database, backups, proxy logs, or Cloudflare configuration were inspected.

## Decision and threat model

Separate the **local display name** from a **public, random Ghost Cloak ID**. A display name is mutable, non-unique profile content, shared with a peer only inside authenticated E2EE content after the current request-privacy gate permits presentation. It never authorizes authentication, recovery, routing, lookup, or uniqueness. A contact's optional local alias is encrypted at rest, never transmitted, and wins over the peer name in that contact's UI. Two people named Alex remain distinct by account/device binding, pinned Signal identity, and Ghost Cloak ID. A peer-provided name is a claim, not verification.

The server may know the Ghost Cloak ID for exact lookup. It must not receive display names, aliases, or contact labels. This removes plaintext human names from the **new steady-state protocol and database**, not unavoidable metadata such as IPs, request times, account/device/routing IDs, prekeys, encrypted mailbox and blob sizes, or social edges observable through lookups and sends. A public ID is pseudonymous metadata; do not put it in release logs, analytics, crash reports, or diagnostic hashes.

## Exact ID format, randomness, and scale

Alphabet: `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 distinct ASCII symbols; excludes `0`, `O`, `1`, `I`, `L`). Canonical form is exactly 12 uppercase characters, e.g. `7K4M9Q2FX8DR`; display form inserts hyphens at positions 4 and 8: `7K4M-9Q2F-X8DR`. Input is case-insensitive ASCII. Accept either exactly 12 unhyphenated characters or exactly the `4-4-4` layout; reject all other punctuation, whitespace, Unicode confusables, and malformed lengths **before** a network request. Normalize to canonical uppercase on both client and server. IDs are immutable and not secret.

Generate 12 independent uniform alphabet indices with an OS-backed CSPRNG (`SecureRandom` on JVM/Android). A simple unbiased method consumes random 5-bit values and rejects `31` before indexing the 31-symbol alphabet. Do not use modulo 31, timestamps, counters, account/key hashes, usernames, or predictable collision suffixes. The durable first-registration intent must retain its candidate over retry after a lost response; generate a new independent candidate **only** after an authenticated registration attempt is authoritatively rejected for an actual ID collision. Bound to five complete candidates, then fail generically and require a later user retry. Do not equate all HTTP 409s with ID collision: account/device/auth-key conflicts still require recovery investigation. The database UNIQUE index is authoritative; concurrent registrations must not rely only on a precheck. Never recycle retired IDs in the initial design.

Space `31^12 = 787,662,783,788,549,761` (59.4504 bits). Approximate probability of at least one collision among independently generated IDs, before retries:

| Accounts | Birthday collision probability |
|---:|---:|
| 100,000 | `6.35 × 10^-9` |
| 1,000,000 | `6.35 × 10^-7` |
| 10,000,000 | `6.35 × 10^-5` |
| 100,000,000 | `0.00633` (about 0.63%) |

At 100 million existing IDs, one fresh candidate collides with probability about `1.27 × 10^-10`; independent retry makes exhaustion negligible. Twelve symbols are acceptable for this design's scale, provided the UNIQUE constraint and five-attempt policy exist. Reassess before materially larger scale or if an additional check character is desired; a check character must not be counted as random entropy. Randomness hinders blind scanning but does not replace authenticated, rate-limited lookup or protect a shared ID from disclosure.

Authentication is already separate from username: `MailboxService.login` verifies a challenge with the stored device-auth public key and original account/device tuple; `recoveryIssue` issues a uniform challenge for a public key and device ID, and `recover` verifies proof against the already-bound server key before returning the original binding. Neither uses username as ownership proof. `EndpointNetworkState` retains host-scoped account/routing/registered/session metadata and a Keystore-backed device credential. The current `connect` uses the local username only in the **durably authorized new-account** path. It must remain impossible for an absent marker, expired token, or 401 to authorize new registration. Ghost Cloak ID also is never a password or recovery credential.

The current server `ServerLogger` records operation/result categories, not names; production HTTP exceptions are generalized. The v1 request body still contains username, and DB/backups do. Reverse proxy, platform, and Cloudflare logging/retention are outside this source audit; inspect their configuration before claiming end-to-end removal. PostgreSQL `rate_limits.principal` contains a SHA-256 of a session device ID or `anonymous`, not username. `attachment_blobs`/`attachment_budgets` refer to account/device IDs. No schema table stores contact labels, but directory/send traffic can reveal relationships to an operator.

## Target protocol and server model

Keep current opaque `accounts.id VARCHAR(36)` and `devices`/routing/auth-key/Signal-key relationships. A later additive migration (candidate **V007**, because source currently ends at V006) adds `accounts.ghostcloak_id VARCHAR(12) COLLATE "C"`, initially nullable, then `NOT NULL` after complete verified backfill. Use a CHECK such as `ghostcloak_id ~ '^[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{12}$'` and a UNIQUE index/constraint; confirm PostgreSQL collation/regex behavior on the target version. Canonical uppercase only; no `display_name` column. Preserve existing account/device primary keys and all foreign keys. A final **separate, reviewed migration after old clients are retired** removes username, its UNIQUE and CHECK constraints; do not edit V001 or assume a safe migration number beyond V006 without checking main at implementation time. Check actual backup/replica/log retention separately; dropping a live column does not erase historical backups or WAL immediately.

Use a deliberately versioned new registration and exact-ID directory contract rather than silently reinterpreting v1 `username`: strict canonical CBOR, existing request-size ceilings and device-auth challenge transcript must be reviewed together. The registration proof must bind the new ID and existing account/device/routing IDs; the server must not let knowledge of an ID log in, reclaim, rename, or replace a device key. The success response should return the authoritative assigned ID to the already-authenticated device, so it can commit the binding atomically to its encrypted endpoint state. New directory responses need account/device/routing and public bundle/capability data, with no name. Preserve one-time-prekey atomic allocation, session renewal, ACK, and attachment capabilities. Lookup requires an authenticated session and a limit on attempts per caller plus global/ingress controls; avoid reflecting distinct unknown vs exhausted/prekey-unavailable states. A successful exact lookup necessarily reveals that some ID is active: this remains an existence oracle to someone who already knows or guesses a valid ID. Do not claim constant-time behavior or full relationship hiding.

Current `CapabilityLookup(deviceId)` is a second directory response path and must stop returning usernames. `Fetch(includeSenders)` currently supplies server-known `SenderProfile.username` for unknown senders. A new sender profile should carry only stable binding fields needed to authenticate/decrypt/route and optionally the public ID; never use it to decide whether a request may be shown. Existing request rows are hidden by default, have a commit-relative grace clock, and blocked senders are authenticated/deduplicated without parsing content. Preserve that entire sequence.

## E2EE name exchange and local contact model

The current `ConversationPayload` has a fixed authenticated framed layout (version 1, text/control/attachment types, 16 KiB bound, random padding and a separate attachment-support marker). It has **no profile-name field**. Do not reinterpret random padding or append a name that v1 decoders might treat as text. Design a distinct versioned, length-bounded authenticated profile extension or profile-control payload and prove downgrade/legacy behavior; keep names out of routing headers, server sender profiles, contact-card QR, notification text before unlock, and backend metadata. Store a received name only after authenticated Signal decrypt, identity/device binding and durable commit. For unknown senders, keep current generic/hidden request presentation until acceptance and required identity review; the encrypted name may be committed privately but must not be rendered early. A change of peer name must not alter an existing local alias, pinned identity, block state, or request state. A same-name duplicate must not merge contacts.

The local contact record currently has one `displayName` and keys by remote device ID. Migrate it transactionally to separate `peerDisplayName?`, `localAlias?`, `ghostcloakId?` while retaining account/device IDs and pinned Signal identity; never infer a shared person from equal names. Bind ID changes to authenticated account proof or a reviewed migration claim; reject an unexplained ID-to-account mismatch. Existing v1 plaintext `ContactCard.username` is neither signed profile content nor safe as a new display name source. A new QR/share payload should be a bounded, versioned contact card (scheme to be decided after Android App Link/deep-link review), containing the canonical ID only or ID plus verified identity fingerprint/material if the UX explicitly offers out-of-band verification. Reject malformed/multiple IDs, huge payloads, unexpected hosts/schemes and untrusted intents; never silently mark a contact verified on scanning a bare ID. Copy/share ID does not share the local display name by default. System share targets may retain copied ID.

## Migration, recovery, and compatibility gates

1. Audit deployed schema version, row constraints, app distribution/signing and backup/rollback window. Freeze no account or key state based on username. Inventory counts only; no user data dump is needed for design approval.
2. Add and validate nullable ID column/index in a reviewed migration. Prefer **server-generated independent CSPRNG IDs for existing accounts**, under serialized/unique DB transaction and bounded retry, because those accounts already have an authoritative server row and may be offline for months. Do not derive an ID from username or require a device to reconnect to complete backfill. Backfill all rows and verify unique/non-null/format counts before enforcing NOT NULL. A separately authenticated client-generated candidate is reasonable for new registration, but existing-account backfill must not transfer ownership or replace auth keys. New clients obtain the authoritative ID only through the existing device-authenticated session or recovery proof; pin it locally against account ID. Lost-response retries are idempotent.
3. Deploy a backend that can serve **both** versioned old and new clients during a bounded upgrade window, with legacy username column/lookup/rename retained only temporarily. New clients must never put a display name into legacy `Registration.username` as an expedient fallback. New accounts should use the new contract; decide how old clients discover them (likely they cannot) and surface an upgrade requirement. Monitor only aggregate old-client usage, no names/IDs. Update Android in place; preserve endpoint host, SQLCipher data, Signal keys, device-auth alias, account/device IDs, sessions, contacts, outbox and attachments.
4. Establish a minimum client version and require old clients to upgrade **before** disabling v1 username endpoints. Legacy clients cannot parse a username-free v1 `DirectoryEntry`/`SenderProfile`; silently dropping the field would break first contact. After an explicit support/deadline decision, stop legacy registration, rename and lookup; then run a separate migration dropping username storage. Old binaries must fail with a clear upgrade-required error and must not register a replacement identity. Rollback to an old backend after column removal is not safe without a controlled schema/data restoration plan; retain reviewed backups with known retention and disclose that historical names can persist there until expiry.
5. Confirm device-key recovery still works when local metadata is missing: current recovery uses `authPublicKey + original deviceId` and returns `RecoveredBinding(accountId,deviceId,routingId,session)` after proof. Extend the authenticated result with authoritative Ghost Cloak ID, or fetch it immediately through the recovered session, and atomically persist it with existing binding. The ID alone is never recovery proof. If the original auth private key is absent, do not recover by ID, username, Signal public key, or a newly generated key. Explicit logout stays separate and blocks automatic reconnect. Background sync never initiates recovery.

The staged path is necessary: removing `username NOT NULL` or changing strict v1 structures in one deployment would break existing clients and users. This is an **implementation gate**, not a reason to abandon the target. No production migration or rollout is authorized by this document.

## Safe Exit and future inactivity feature

The existing Safe Exit wipes local cryptographic secrets and app-owned encrypted state before fresh onboarding. The new local name, ID association, aliases, request/contact data and any cached QR must live in that same destructible state, not an unguarded preference or backup. Verify process-death/reboot completion and no silent old-account reconnect. A server account may remain but cannot be accessed without approved recovery proof. Future inactivity-triggered Safe Exit can reuse this lifecycle; it has no server-side ID revocation requirement and is not designed or implemented here.

## Implementation and acceptance plan (future phases only)

Tests: uniform generator and independent collisions; 100k/1M/10M/100M calculation; parser case/format/confusables; DB UNIQUE race and bounded retry without an account-existence leak; two Alex display names with distinct IDs and block/pin/contact/request handling; unknown/exhausted lookup rate limits; sender-profile privacy and first encrypted name exchange; hidden request, blocked decrypt/ACK, replay and downgrade behavior; local alias persistence and E2EE exclusion; offline existing-account backfill with same Signal/device-auth keys and history; lost response/restart; 401 renewal and device-key recovery without username; legacy/new coexistence and enforced upgrade; no-name DB/log dump for synthetic Alex/Alex/Esaie; Safe Exit then onboarding without restoration. Use isolated PostgreSQL and disposable AVD fixtures. Do not run instrumentation on physical phones or inspect live private phone data. Check no name/ID in notifications, WorkManager names/tags/input, or release diagnostics.

**Blockers before implementation approval:** current v1 registration hash includes username; current v1 directory, capability refresh and `Fetch(includeSenders)` return it; current contact card and first-request contact creation depend on it; current Android local identity field conflates username/display name; old clients cannot parse name-free v1 responses; deployed DB/log/backup state is unverified. These require explicit versioning, a staged forced-upgrade window, transactional local migration, and deployment review. The cryptographic recovery design itself does **not** require username ownership, and the proposed 12-symbol ID is sufficiently large at 100 million accounts, but implementation is **not yet safe to deploy** until these gates are designed and tested in a subsequent phase.

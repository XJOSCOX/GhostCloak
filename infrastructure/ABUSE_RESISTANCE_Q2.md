# Phase 1Q.2 abuse resistance and rollout

This change is source-only. The operator will deploy the backend, additive V008, nginx route, and compatible Android build. No live server or physical phone was touched here.

## Q-02: anonymous challenge and recovery

Preauthentication request families use fixed one-minute buckets. Recovery issue is partitioned by the SHA-256 digest of the supplied auth public key; recovery verify uses the supplied key and challenge ID. Ordinary challenge issuance uses supplied account/device IDs and registration hash, whether or not any account exists. This input is not accepted as ownership proof and is never returned. Each such bucket allows 10 requests per minute; challenge issuance and recovery issuance additionally share a broad 600/minute emergency ceiling. The backend continues to bound active challenges to 1,000, expires them after at most two minutes, and consumes a verification challenge once even on bad proof. A caller with many independently generated keys can still consume global capacity; without client identity, proof of work, or trusted edge abuse protection, Sybil starvation cannot be eliminated. Coarse edge/origin limits should be configured independently of account existence and must not forward visitor IP to application code.

Known and unknown recovery targets use the same bucket selection before account lookup and retain the same public challenge and failed-proof shapes. No raw IP, cookie, device fingerprint, or plaintext recovery relationship is added to backend tables. Rate-limit rows contain a hash of the request-material digest and expire on the existing minute cleanup.

## Q-03: discovery and allocation

`/v2/directory/lookup` returns only stable public directory summary and does not remove a one-time prekey. An unavailable or exhausted target returns the same generic unavailable response. `/v2/directory/prekey` requires a valid requester session, target Ghost Cloak ID, and a client-generated UUID allocation ID. The backend serializes allocation, stores the public bundle and requester/target binding atomically with removal from the target pool, and returns the same bundle for the same requester and ID after a lost response. Reusing the ID with another target fails. A new allocation is limited to 2 per requester/target per minute, 60 per requester per minute, 4 retained per requester/target, 64 retained per requester, and 10,000 retained globally. Unknown and known targets are charged before lookup. These limits deliberately bound abuse at the cost of limiting rapid new conversations with the same target.

The Android add-contact flow stores the allocation ID in its encrypted endpoint store before the request and reuses it after process restart. It stops retrying after 23 hours or local clock rollback rather than risk requesting a new bundle after response expiry. On the server, the public bundle is available for retry for 24 hours; cleanup removes bundle bytes and retains a terminal tombstone for 48 hours. Cleanup is indexed and bounded. The tombstone retains only the already server-visible requester/target device relationship and opaque ID for that period; it does not add a Ghost Cloak ID column. Allocation does not regenerate an identity or Signal keys. Existing automatic refill remains target 16, below 4, using authenticated publication. The signed attachment capability remains on the allocated bundle, so the first photo/document request can still be prepared without a reply.

## Deployment and rollback

Freeze writes and back up the current V007 database and blob store with protected digests. Install the reviewed backend artifact and apply its packaged **V008** through the dedicated migrator before enabling the new Android build. V008 adds `prekey_allocations` with a primary-key allocation ID, requester and target device foreign keys, nullable bounded public bundle, response and tombstone expiry timestamps, and expiry/requester indexes. It does not delete accounts, devices, messages, or prekeys. Update the nginx origin route allowlist for `/v2/directory/prekey`; syntax-check and reload the origin only after the backend is ready. Then install the compatible Android build in place and test two disposable accounts: 100+ lookups leave target inventory unchanged, first text and first photo/document requests work, a repeated allocation ID returns the same key, and prekey refill restores the pool. Inspect only sanitized rate/result categories.

Old clients expect a bundle from lookup and cannot initiate new contacts against the changed backend. Plan a coordinated client/backend rollout. If the rollout fails, stop new allocations and restore the matching V007 backup plus prior backend and ingress/client set. Merely downgrading code against a V008 schema is not an endorsed rollback; never truncate V008 or reset accounts to force compatibility. Keep any collected backup under the existing protected retention policy.

# Key lifecycle

Identity: generated by libsignal once per endpoint. Private identity serializations are stored only in the Keystore-rooted SQLCipher database and authenticate establishment, not chat bodies. User and device UUIDs use SecureRandom-backed UUID generation. Corrupt or inaccessible storage must fail rather than regenerate identity.

Prekeys: PreKeyManager owns local creation, explicit replenishment, inventory and retirement. `publicBundle` delegates to it. Each bundle includes an EC one-time key, a signed EC key and a signed one-time Kyber key. Libsignal consumes the one-time private records transactionally on acceptance; signed keys remain for delayed establishment. There is no publisher, scheduler, network or production key server.

Local prototype policy: target one unused bundle, at most 32 retained signed-key bundles, and a 30-day retention target from creation. `replenishIfNeeded` returns public bundles for a future caller to publish; it does not send them. `retireExpiredKeys` deletes expired signed/private one-time records only on explicit invocation. Thus 30 days is enforced when maintenance runs, not a promise of background expiration. A wall clock is a policy input, not a rollback-resistant clock. At quota exhaustion creation fails with ResourceLimit and never removes live keys silently. The production publication/expiration/delayed-delivery contract remains a review blocker.

Keys used by an established ratchet are in its session record, so retiring establishment keys does not intentionally destroy active sessions. An undelivered first prekey message still needs its establishment keys: deleting those prematurely can make it undecryptable. Tests show acceptance within the 29-day fixture window and rejection after explicit retirement at 31 days. No unlimited delayed-delivery guarantee is made. Last-resort Kyber keys, publication retries and automatic maintenance remain unimplemented.

ID review: the pinned PreKeyBundle API has distinct EC, signed and Kyber ID fields; PreKeyStore, SignedPreKeyStore and KyberPreKeyStore look up distinct record types. Equal numeric IDs in those namespaces are consistent with these APIs; they do not denote the same key. Phase 1A.1 nevertheless allocates independently and uses different numbers within each new bundle for clarity, while retaining issued-ID markers to avoid reuse. Existing Phase 1A keys retain their original IDs and timestamps. Migration never renumbers cryptographic records. Issued-ID allocation is capped at 10,000 per namespace and fails explicitly at the bound. See the source links in CRYPTO_DEPENDENCIES.md.

Sessions: library serialized records contain evolving ratchet state and bounded skipped-message keys. All callbacks are backed by one database transaction; no cached mutable session survives failure. Message keys are managed and discarded by libsignal. Public counters and changed public ratchet keys demonstrate progression in tests; they do not prove cryptographic forward secrecy or physical erasure.

Destruction: remove the session record, retain identity trust and accepted-envelope records, and persist DESTROYED. Old Phase 1A deny markers migrate to that state. Explicit fingerprint-validated reconnection is described in PROTOCOL.md; merely receiving an old prekey packet cannot clear the state. No claim of wiping peer copies, old database pages, snapshots, flash wear-leveling remnants, OS memory or native-library buffers is made.

Storage: a 32-byte random database secret is wrapped using AES-GCM with a nonexportable Android Keystore key, unique per local endpoint. JCA generates each wrapping IV; alias-bound associated data prevents accidental cross-endpoint substitution. Wrapped files and database live in noBackupFilesDir. Android backups and cleartext networking are disabled. Software-backed Keystore is permitted; KeyInfo reports reduced protection internally. User-authentication gating is not enabled in this phase, so app-process compromise can use an unlocked database.

Kotlin/JVM and JNI do not guarantee perfect wiping. Mutable serialized secret arrays are overwritten where practical, but library objects, Room/SQLCipher buffers, GC copies and native handles may outlive an operation. The database connection retains necessary key material until closed. Avoid unnecessary secret strings and logging. Phase 1B stores serialized local message history only inside the encrypted endpoint-record table; UI rendering necessarily holds plaintext Strings in memory. There is no separate plaintext database.

SQLCipher's connection pool can open new read connections after initial database opening. Retain its password buffer until the entire Room database is closed, then overwrite the owned buffer. Wiping immediately after opening breaks later connections; the Android rollback/read test covers this regression. This required lifetime does not authorize exporting or logging the secret.

# Public prekeys and encrypted mailbox

> **HISTORICAL PHASE SNAPSHOT.** The implementation and rollout statements below record their phase and may predate v2 Ghost Cloak IDs, V007/V008, seven-day mailbox expiry, and later privacy controls. Use the [current audit](../SECURITY_AUDIT_CURRENT.md) and [deployment runbook](../infrastructure/DEPLOYMENT.md) for current status; do not execute old route or migration instructions against a live target.

The backend stores existing libsignal public structures; it does not implement X3DH/PQXDH or deserialize Signal ciphertext. `EnvelopeCodec` validates only outer protocol/routing framing. Endpoint libsignal verifies signed/PQ public keys and performs encryption/decryption. The backend has no endpoint crypto/storage dependency and no decryption API.

## Directory/prekey policy

Each published pool entry is the existing complete RemoteKeyBundle: identity, signed EC prekey/signature, one-time EC prekey and one-time KYBER_1024 prekey/signature. Fetch atomically removes one whole entry, including its EC/PQ components, under the repository transaction. Empty pool returns prekeys_exhausted; no invented last-resort or unsigned fallback. Retries of a lost directory response can consume another entry. This is an availability/privacy risk, not key reuse.

Pool capacity is 32, upload count 1–16. Device ownership, identity continuity, serialized size, key shape and duplicate EC/PQ IDs are checked. Consumed IDs are retained so they cannot be reintroduced. Each signed ID must always refer to the same public key/signature bytes. The existing endpoint generator creates a new signed/EC/PQ tuple per publication; server preserves those associations rather than substituting a global newest signed key into an older tuple. Issued EC/PQ/signed histories are bounded at 10,000 per device; exhaustion fails closed and requires future lifecycle design. This is not a production rotation service. The endpoint's existing signed/private-key retention (30 days) exceeds the default mailbox TTL. The backend cannot prove possession of Signal private prekeys; malicious/malformed signatures are rejected by the session-establishing endpoint, not validated with a homemade server scheme.

## Delivery and retention

Phase 1E.1 adds optional authenticated Fetch sender profiles and sender-scoped receipt queries. The successful recipient ACK atomically marks the existing submission row acknowledged before removing mailbox ciphertext. The boolean expires with that row; it adds no read state or delivery timestamp. Expiry or missing ciphertext never implies delivery. Optional bounded skip IDs allow later messages to be fetched without ACKing rejected/blocked envelopes. See [the Phase 1E.1 contract and rollout](../SECURITY_REVIEW_PHASE_1E1.md) for compatibility, V002 migration and request trust rules. The retention details below still apply; ACK now records this bounded boolean in addition to removing the queue entry.

Routing ID is an independently random UUID, not username, hardware identity or a hash of a public key. It stays stable across username changes. It separates public discovery from delivery addressing but is not a secret or an anonymity measure. Server account records can link all these identifiers.

Authenticated send verifies the outer sender equals session device and outer recipient equals the device registered at the destination routing ID. Maximum encoded envelope: 128 KiB. Destination quota: 128 records and 8 MiB; global mailbox quota: 2,048 records. No ciphertext body analysis, moderation/decryption or conversation reconstruction API exists. Server records: random server ID, recipient routing, opaque encoded envelope, receive time and expiry.

Default encrypted-mailbox TTL is **24 hours**, configurable from one second (tests) to seven days. Fetch returns at most eight oldest records without deleting or marking permanent delivery. Recipient must explicitly ACK after accepted endpoint processing. ACK rejects known records owned by another recipient before changing any rows; repeated/missing/expired IDs are no-ops. ACK only removes queue records, not copies a malicious server may have made. Tests prove fetch/ACK isolation and replay rejection at the endpoint. `receive()` exposes unacknowledged envelopes for transport compatibility; an ACK-aware controller must use fetch/acknowledgeAccepted. A collector returning is not an ACK.

The original v2 submission ID was a random local UUID. Dedupe key is (authenticated sender device, submission ID); stored digest binds recipient routing plus exact envelope bytes. Matching retry returns the original server ID, including after ACK/expiry. Different bytes/routing with the same submission ID returns conflict. Legacy UUID receipt rows remain indefinitely in the current implementation; the configured 30-day `expires_at` value is not a deletion policy. Sender quota remains 1,024 rows; global quota remains 10,000. No receipt cleanup or capacity increase is authorized by P13.3B.

**P13.3B current contract.** Protocol-v2 `Send` also accepts a distinguishable `s3` transport ID: the exact ASCII prefix `s3` plus unpadded canonical base64url of 23 bytes: version byte `0x03`, unsigned 48-bit big-endian expiry in Unix milliseconds, and 16 bytes from `SecureRandom`. It is exactly 33 characters, so a 36-character sender UUID, separator and ID fit the existing 73-character SQL key. No recipient, message type, conversation or group identity is encoded. Invalid length, encoding, version or zero timestamp is rejected. The server checks the embedded deadline before any receipt lookup or mailbox write: `serverNow > expiry` returns HTTP 410; `expiry > serverNow + 14 days` is rejected. An accepted ID keeps one digest-bound result through expiry. If its receipt is absent after expiry, status lookup returns `unavailable`, not delivered or undelivered. Once expired, even deleting the receipt cannot make the old ID sendable again. The 14-day maximum exceeds the seven-day mailbox TTL and 24-hour unassigned-offline window; Android generates at trusted server time + 13 days 23 hours to allow one hour for transport skew/latency. P13.3B **does not delete receipts**. Future P13.3A retirement must preserve each V3 receipt at least through its intrinsic expiry and separately decide the legacy-UUID policy before changing quotas.

The timestamp reveals an approximate expiry to the server, which already sees SEND time and routing metadata. A malicious sender can use a fresh ID for the same old ciphertext; server idempotency cannot prevent that, while the receiving endpoint's durable envelope replay ledger prevents a second application delivery. Do not log complete IDs or envelope bytes. Roll out the new backend first, then updated clients; old UUID clients remain supported in this stage. A later cutoff for *new* legacy UUID sends needs explicit approval and updated-client validation. Existing UUID rows/status queries remain available. Existing `/v2/messages` and nginx routes are unchanged.

`cleanup()` deletes expired challenges, sessions, mailbox records and dedupe rows, and is invoked before every request. A completely idle in-memory backend does not wake just to purge; expired rows are inaccessible on the next operation and explicit cleanup is callable. A persistent adapter needs a scheduled expiry job with deletion/backup policies. No long-term archive API exists. Stopping the local server discards all in-memory state, so this phase provides offline delivery across client disconnects, not backend-restart durability.

## Repository contract

AccountRepository, DeviceRepository, PreKeyRepository, MailboxRepository, ChallengeRepository and SessionRepository expose typed rows behind BackendDatabase.transaction. The memory adapter requires transaction ownership on every table access and rolls back failures using a copied serialized state. Challenge claim is a separate committed transaction. Service input/output is copied so callers cannot mutate repository byte arrays outside a transaction.

A PostgreSQL implementation must use serializable transactions or equivalent locking/unique constraints for username/device/routing/auth-key uniqueness, challenge claim, one-time prekey consumption, quota checks, send dedupe and owner ACK. Every quota check and write must be atomic. The bounded memory adapter scans rows and copies state and is intentionally not a production-performance implementation. No database listener, credentials, production migrations or deployment are included.

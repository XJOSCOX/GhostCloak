# Key lifecycle

Identity: generated by libsignal once per endpoint. Private identity serializations are stored only in the Keystore-rooted SQLCipher database and authenticate establishment, not chat bodies. User and device UUIDs use SecureRandom-backed UUID generation. Corrupt or inaccessible storage must fail rather than regenerate identity.

Prekeys: each publicBundle call creates an EC one-time prekey, signed EC prekey and signed one-time Kyber prekey. The library consumes one-time private records transactionally after acceptance. Signed keys remain for delayed delivery. The prototype allows at most 32 issued bundles and stops on exhaustion. Automatic rotation, expiry, publication retries and replenishment are Phase 1B blockers, not improvised here. Only one-time Kyber keys are used; no last-resort key reuse is supported.

Sessions: library serialized records contain evolving ratchet state and bounded skipped-message keys. All callbacks are backed by one database transaction; no cached mutable session survives failure. Message keys are managed and discarded by libsignal. Public counters and changed public ratchet keys demonstrate progression in tests; they do not prove cryptographic forward secrecy or physical erasure.

Destruction: remove the session record while retaining the contact identity pin and deny marker. It does not wipe peer copies, old database pages, snapshots, flash wear-leveling remnants, OS memory or native-library buffers. No claim of deterministic forensic erasure is made. Prototype tombstones intentionally prevent session resurrection and cannot yet be reset through an application API.

Storage: a 32-byte random database secret is wrapped using AES-GCM with a nonexportable Android Keystore key, unique per local endpoint. JCA generates each wrapping IV; alias-bound associated data prevents accidental cross-endpoint substitution. Wrapped files and database live in noBackupFilesDir. Android backups and cleartext networking are disabled. Software-backed Keystore is permitted; KeyInfo reports reduced protection internally. User-authentication gating is not enabled in this phase, so app-process compromise can use an unlocked database.

Kotlin/JVM and JNI do not guarantee perfect wiping. Mutable serialized secret arrays are overwritten where practical, but library objects, Room/SQLCipher buffers, GC copies and native handles may outlive an operation. The database connection retains necessary key material until closed. Avoid secret strings and logging. No plaintext message table exists.

SQLCipher's connection pool can open new read connections after initial database opening. Retain its password buffer until the entire Room database is closed, then overwrite the owned buffer. Wiping immediately after opening breaks later connections; the Android rollback/read test covers this regression. This required lifetime does not authorize exporting or logging the secret.

# Ghost Cloak v2 / V007–V008 deployment runbook

This is the current source runbook. The [Phase 1C2 instructions](DEPLOYMENT_PHASE_1C2_HISTORICAL.md) and [v1 API notes](../protocol/API_V1.md) are historical. This file documents a procedure; it does not attest that a particular VPS, database, backup, or phone has been inspected. The operator owns the deployment and must authorize every destructive step. Do not apply `migrate` to an unreviewed database.

## Contract and migration boundary

The Android and backend source use `/v2` account, auth, directory, prekey and mailbox routes. Public addressing is by a random 12-character Ghost Cloak ID. A display name is local/E2EE profile data, not a server username. Attachment routes remain under `/v1/attachments`; the nginx allowlist needs the [separate attachment route fragment](attachments.nginx.conf.fragment) alongside the [v2 origin template](tunnel/nginx-origin.conf.template). Review their combined syntax and method/body limits for the deployed artifact. The server migration chain is V001 through [V008](../backend/src/main/resources/db/V008__prekey_allocation_retry.sql). V007 **deletes all rows** in 13 identity-bound tables, then drops `accounts.username` and adds constrained `accounts.ghostcloak_id`. It is not an in-place account conversion. V008 is additive and creates a bounded retry table for prekey allocation; follow [the Q.2 rollout note](ABUSE_RESISTANCE_Q2.md) for its coordinated backend/Android deployment. An existing account cannot be recovered by knowing its Ghost Cloak ID alone.

## Before touching the server

1. Pin and record the Android/backend source commit, migration checksums, backend artifact digest, deployment target and maintenance window. Check the release build's API origin. Coordinate compatible Android/backend versions and notify test-account owners that V007 resets server continuity if that cutover is approved.
2. Inspect the destination schema history and row counts for **every V007 deletion target**: `attachment_budgets`, `attachment_blobs`, `message_deduplication`, `mailbox_messages`, `prekey_bundles`, `one_time_prekeys`, `pq_prekeys`, `signed_prekeys`, `access_sessions`, `auth_challenges`, `rate_limits`, `devices`, and `accounts`. Also inventory owned blob files. Save only sanitized counts in the change record; do not copy identifiers, ciphertext or credentials into logs.
3. If V007 is absent and any target contains data, **stop** until the operator explicitly approves permanent loss of that target's account continuity and queued content. A nonempty production database is not implicitly disposable. Obtain a consistent database backup and blob-file backup, record protected locations and integrity digests, and rehearse restoring them into an isolated destination before proceeding. Keep backup access and retention limited.
4. Freeze writes, take a final consistent backup and verify its digest. Pin the dedicated migrator to the exact reviewed immutable backend release; keep its credentials separate from the serving process. Deploy that compatible backend artifact and only then invoke its packaged migrator against the authorized target. Never edit an applied V007 checksum or manually fake schema-history success. Keep any app client whose protocol is incompatible offline until the backend is ready.
5. Inspect migration status and schema: exactly one V007 history entry with expected checksum; `accounts.username` absent; `ghostcloak_id` present, unique, non-null, and constrained to the canonical alphabet/length; the 13 reset tables empty immediately after cutover. Verify ordered migration checksums and relevant indexes/constraints. Review orphan blob files separately; SQL metadata deletion does not erase filesystem blobs. Avoid logging any account or blob identifier.
6. Verify `/health` and the reviewed route allowlist, HTTPS origin isolation, no unauthenticated alternate routes, controlled registration/challenge renewal, prekey publishing, exact-ID lookup, text delivery and attachment capability flow using disposable accounts. Verify generic error behavior and metadata/log policy. Only then allow compatible Android clients to connect.

## Rollback and recovery

V007 cannot be reversed by redeploying old code: it destroys account and queue rows and changes the schema. If cutover fails, stop writes and restore the **matching pre-cutover database and blob backup** into an isolated, verified environment; reconcile schema history and the matching old backend, Android client, and ingress route set there before traffic moves. Restore the complete set together, not selected account rows. A post-cutover account must not be merged into the old database without a separately designed migration. If restore was not rehearsed, report that limitation and do not claim a proven rollback. Preserve protected backups under the approved retention policy.

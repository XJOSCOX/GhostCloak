# Phase 1L — pre-release anonymous identity cutover

Ghost Cloak has two separate profile concepts. The **display name** is mutable, non-unique, encrypted local profile data and may reach a peer only within authenticated end-to-end encrypted message content. The **Ghost Cloak ID** is the immutable, public, random, server-assigned lookup handle. Neither a display name nor knowledge of an ID proves account ownership. Account/device authentication and recovery continue to require the existing device-auth cryptographic proof.

This is an intentional pre-release break. Username-based clients and test data are incompatible. There is no dual protocol, username lookup, rename, or plaintext-name server column. Existing local test installations may need an explicit local reset; the app must not silently generate a replacement identity after reading incompatible state. Safe Exit removes the encrypted local display name, assigned ID, account binding, contacts, messages and keys, then returns to fresh onboarding without reconnecting to the old account. Server accounts are not remotely erased by Safe Exit.

## ID format and generation

The alphabet is `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (31 symbols). Storage and protocol use twelve uppercase symbols, e.g. `7K4M9Q2FX8DR`; UI groups them as `7K4M-9Q2F-X8DR`. Manual entry accepts exactly either ungrouped or `4-4-4`, case-insensitively, and rejects whitespace, non-ASCII lookalikes and ambiguous `0/O/1/I/L`. The space is `31^12 = 787,662,783,788,549,761` (approximately 59.45 bits).

The server uses `java.security.SecureRandom`. For each symbol it draws a uniform five-bit value with `nextInt(32)`, discards 31 and indexes the alphabet. Every collision causes a completely independent candidate, at most five candidates per registration. PostgreSQL's unique constraint is the final safeguard; the registration transaction serializes allocation with other database writes. A collision never triggers a predictable increment. The public ID is pseudonymous metadata, never a secret or authentication credential.

## Server contract and migration

V007 resets only identity-bound disposable pre-release rows, in this explicit order: `attachment_budgets`, `attachment_blobs`, `message_deduplication`, `mailbox_messages`, `prekey_bundles`, `one_time_prekeys`, `pq_prekeys`, `signed_prekeys`, `access_sessions`, `auth_challenges`, `rate_limits`, `devices`, `accounts`. It drops `accounts.username` and adds `accounts.ghostcloak_id varchar(12) COLLATE "C" NOT NULL UNIQUE` with an approved-alphabet format CHECK. Existing account primary key, device and routing fields remain in the schema. No display-name or alias column is added. Existing encrypted blob files in `GHOSTCLOAK_ATTACHMENTS_DIR` are outside the SQL migration; after stopping the old service, the operator must separately inventory and retire disposable orphan files under the reviewed blob-retention procedure. Historical V001 migration text and old backups/WAL may still contain former test usernames until their separate retention expires; the live final schema does not.

The mailbox/auth wire contract is version 2. Registration carries cryptographic account/device/routing/key material, **no name and no client-selected ID**. The server returns its assigned ID after registration, and the client stores it with the authenticated session in encrypted endpoint records. Directory lookup is an authenticated, rate-limited, exact canonical-ID query, with no prefix search or bulk endpoint. Directory and sender profiles contain the public ID and required account/device/routing/key data, never a human name. The attachment blob service retains its separate version-1 endpoint and opaque encrypted-blob contract. The old account username rename endpoint is gone.

The ID alone cannot issue a valid login, recover an account, replace an auth key or rebind a device. A normal expired session renews with the stored device-auth key. Missing network metadata requires the existing proof-based recovery flow; the authenticated recovery result includes the authoritative ID. Explicit logout remains a barrier to automatic reconnect and WorkManager registration remains prohibited.

## Android profile and request privacy

The owner chooses a display name before local identity creation. It is stored in the encrypted endpoint store under a local profile record, never sent with registration. Local rename changes only that record; it does not rotate Signal identity, account ID, Ghost Cloak ID or device credential. Future text and attachment E2EE payloads carry a bounded, versioned authenticated profile name marker. Recipients must decrypt/authenticate before storing it. An unaccepted message request keeps the peer-provided name and content hidden in UI until acceptance. A local alias, where present, wins in the accepted contact UI and is never transmitted. Contact security, block state, session and pinning remain bound to account/device/cryptographic identity rather than a name.

Local/demo contact cards use version 2 and contain a public ID plus cryptographic contact material, without a display name. Their locally random ID is a demo-only placeholder, not a registered directory handle; the connected UI uses server-assigned IDs and does not export those cards. A bare ID or card never marks a contact verified. A future QR/deep-link flow needs a separately reviewed parser and identity-verification UX.

## Threat model and residual metadata

Random IDs make guessing impractical at small scale but are not secret. An authenticated successful exact lookup reveals that an ID exists; rate limits and lack of bulk/prefix search constrain enumeration and spam. The server can still observe account/device/routing identifiers, public keys, ciphertext lengths, request times, IP/network data and relationship edges from lookups/sends. Display names, aliases, labels and full Ghost Cloak IDs must not appear in application logs or diagnostic hashes. Fixed-category server logging records only operation/result. Source-level synthetic Alex/Alex/Esaie tests assert that registration bytes and in-memory server database snapshots contain none of those names; production proxy, infrastructure, historical backup and live database retention require separate operational review.

## Deployment and rollback

Do **not** run V007 or deploy the backend as part of this code change. Back up and review the disposable staging database, apply the new backend and V007 together in a controlled maintenance window, then install only Phase 1L Android clients. Existing username clients cannot operate against version 2 and must not silently reinterpret usernames as IDs. V007 intentionally invalidates old test accounts, sessions, prekeys, mailbox, dedupe and attachment ownership. Rolling back only the binary cannot restore deleted rows or the dropped column; rollback requires a tested full database restore and compatible old backend/client set, with attention to any accounts created after cutover. Do not restore old credentials into a newer partial schema.

Physical validation after deployment: on two disposable accounts choose the same display name, confirm distinct IDs, add by exact formatted ID, exchange a hidden first-contact request and accept, verify encrypted profile name, message/attachment delivery and 401 renewal. Check malformed/unknown lookup, rate limit and cryptographic recovery, then Safe Exit on one client. Inspect sanitized DB/schema and logs for absence of names. Never run connected tests on important physical accounts.

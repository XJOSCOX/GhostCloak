# Logging policy

Production uses no access logger, SLF4J NOP, disabled JDBC JUL logging and null service stdout/stderr. Exceptions return fixed protocol errors without stack traces. nginx access and error logging are disabled because native error records can contain request URLs and client addresses. Do not enable request tracing, HTTP debug, SQL parameter logging, heap dumps or core dumps. PostgreSQL settings suppress statements, bind parameters and routine connection records; audit the effective server settings and any provider agent, pgAudit or query-statistics extension before staging.

Health returns only ok/unavailable. Monitor process exit status, health availability, disk capacity, certificate expiry and coarse infrastructure load. Loss of detailed logs makes incident diagnosis and abuse attribution harder; that is an explicit prototype tradeoff. Operator debugging must be separately reviewed, restricted, scrubbed before storage and deleted within 24 hours. Never record tokens, challenges, bundles, safety numbers, plaintext or ciphertext bodies.

The historical direct-ingress template keeps bounded volatile IP buckets. The prepared Phase 1D.1 tunnel-origin template replaces these with aggregate hostname budgets and never substitutes the connector's socket address for a visitor identity. PostgreSQL retains only the existing anonymous/device-derived hash bucket, operation and minute, with expiry. Cloudflare edge abuse controls may still use visitor source IP/network signals; their limits are distinct from application quotas. There is no server-side IP reputation database.

The tunnel profile disables automatic request-header forwarding and clears visitor-address headers. Do not install nginx real-IP configuration, Ktor forwarding plugins, access-log modules or application address fingerprinting. Header parsing can still hold client-supplied strings transiently; this is not a guarantee against privileged observation. The VPS sees Cloudflare transport/management traffic after cutover, while Cloudflare still sees client IP, time, TLS/HTTP metadata, paths, hostname and sizes. Existing historical origin exposure remains discoverable.

Cloudflared uses error verbosity with stdout/stderr discarded, no logfile and no account/token environment dumps. Its debug logging can expose headers; never enable it for real traffic or use live tail/diagnostic bundles without a separate reviewed, synthetic-only procedure. Local metrics stay on 127.0.0.1:20241 and are not public health. Monitor only coarse ready/exit/availability status; do not forward detailed metrics containing tunnel IDs/topology to clients. See [cloudflared logging parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/).

In the owner's later Cloudflare configuration, minimize optional analytics, request tracing, Workers, Logpush and unnecessary request-header transforms; bypass cache for this API hostname and review Security Events/Log Explorer retention and available field controls. Plan-specific controls do not establish that Cloudflare stores nothing. The provider can observe TLS-terminated Authorization and protocol bodies, and may retain operational/security records under its policy. No Cloudflare setting was changed here. Disabling origin logs is not IP anonymity.

System service status/OS audit logs may retain account, process and administrative login metadata. Set an operator-reviewed short journal retention (recommended seven days) without weakening required security auditing. Do not claim provider-side retention is controlled by these files. See [PostgreSQL logging controls](https://www.postgresql.org/docs/17/runtime-config-logging.html).
